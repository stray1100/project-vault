精讲 · 深度版（约 3260 字）

一块只有芯片的板子为什么不跑？先问四件事：供电、时钟、复位、启动模式。

为什么要学这个

最小系统是唯一必须自己画对的电路，也是所有后续实验的地基。开发板能跑，不代表你知道它为什么能跑；一旦自己画板、换芯片、改供电，四要素里少一环就是整块板不亮。把这件看似玄学的事拆成四个可测量的物理量，是嵌入式入门真正的第一步——它决定了你后面遇到问题时会去量电压，还是一直改代码。

一、供电不是一路，是五路

VDD 给 IO 环与内核逻辑，通常多组引脚并联，每组旁边必须有 100nF 去耦电容，缺一路并不会立刻坏，而是表现为某个 BANK 的 IO 异常或高负载时随机跑飞。VDDA/VREF+ 是模拟供电，独立引脚独立滤波，ADC 精度直接取决于它是否干净。VCAP_1/VCAP_2 是内核 1.2V 稳压器的外接储能脚，F4 系列要求各接 2.2µF 低 ESR 电容到地，缺它或容值不对，内核电压抖动会让程序在随机位置进 HardFault。VBAT 供 RTC 与备份寄存器，掉电保持时间靠它。

二、时钟有两套，性能与精度分开

HSI 是内部 16MHz RC，上电即可用、无需外部器件，但精度差（室温约 ±1%，全温区更差），只能保证芯片能动，不能保证串口波特率准、定时不漂。HSE 是外部晶振，F407 支持 4–26MHz，经 PLL 倍频可到 168MHz 主频；晶振能否起振取决于负载电容匹配、走线长度与是否包地，起振失败时芯片通常自动退回 HSI 继续跑——这正是最危险的故障：板子看似正常，但通信全部错帧。LSE 是 32.768kHz，专供 RTC。

三、复位是状态机，不是一根线

NRST 低电平复位，芯片内部有弱上拉，外部并 100nF 到地构成上电延时，保证电源爬升期间一直处于复位。但复位源不止引脚：上电/掉电复位（POR/PDR）、欠压复位（BOR）、独立看门狗、窗口看门狗、软件复位都会触发复位。关键是 RCC_CSR 里的标志位会记录"这次是谁把我复位的"，读它比猜快一百倍——尤其是排查"板子每隔几秒自己重启"这类问题时。

四、启动模式决定 0x00000000 指向谁

上电瞬间 CPU 从 0x00000000 取初始 MSP、从 0x00000004 取复位向量，而这两个地址是别名，实际映射由 BOOT0/BOOT1 决定：映射到主 Flash（正常运行）、系统存储器（ST 内置 bootloader，可用串口/USB DFU 救砖）、内置 SRAM（调试用）。BOOT0 悬空最要命——上电那一刻电平不确定，于是"有时能跑有时不能跑"，且换一块板子表现还不一样。

上电第一件事：查明复位来源（寄存器直写，不依赖 HAL）
/* RCC 基址 0x40023800，CSR 偏移 0x74（RM0090 RCC 章） */
#include <stdint.h>

#define RCC_BASE   0x40023800UL
#define RCC_CSR    (*(volatile uint32_t *)(RCC_BASE + 0x74U))
#define CSR_RMVF   (1UL << 24)   /* 清标志位，位号见 RM0090 RCC_CSR */
#define CSR_PINRST (1UL << 26)
#define CSR_PORRST (1UL << 27)
#define CSR_SFTRST (1UL << 28)
#define CSR_IWDGRST (1UL << 29)
#define CSR_WWDGRST (1UL << 30)
#define CSR_LPWRRST (1UL << 31)

typedef enum { RST_PIN, RST_POWER, RST_SOFT, RST_IWDG, RST_WWDG, RST_LOWPWR, RST_UNKNOWN } rst_t;

rst_t reset_cause(void)
{
    uint32_t f = RCC_CSR;          /* 先读，读之前不要清 */
    RCC_CSR |= CSR_RMVF;           /* 清标志，写 1 有效 */
    if (f & CSR_IWDGRST) return RST_IWDG;
    if (f & CSR_WWDGRST) return RST_WWDG;
    if (f & CSR_LPWRRST) return RST_LOWPWR;
    if (f & CSR_SFTRST)  return RST_SOFT;
    if (f & CSR_PINRST)  return RST_PIN;
    if (f & CSR_PORRST)  return RST_POWER;
    return RST_UNKNOWN;
}

工程追问（能答上来才算懂）

VDDA 为什么不能和 VDD 直接短接共用一组去耦？

模拟供电对电源噪声极敏感。数字 IO 翻转产生的开关噪声会通过共用阻抗耦合进 ADC 参考，直接表现为采样值跳动、有效位数下降。即便电压相同也必须单独滤波、单独走线，在芯片下方单点汇合。

VCAP 电容为什么强调低 ESR，随便一颗 2.2µF 不行吗？

VCAP 是内核稳压器的输出储能，负载是 MHz 级跳变的数字逻辑。ESR 高会形成明显的瞬时压降，内核在高速切换时被拉低，表现为随机 HardFault 或数据错误。必须选低 ESR 陶瓷电容，且紧贴引脚布局。

BOOT0 悬空为什么会导致"时好时坏"，而不是干脆不启动？

悬空脚的电压由漏电流、寄生电容和上电斜率共同决定，每次上电的电荷状态可能不同，因此映射目标在 Flash 与系统存储器之间随机跳变。落在系统存储器里就表现为"程序没跑、但芯片是活的"。

精讲 · 深度版（约 3114 字）

编译器不是一步到位的黑盒：预处理、编译、汇编、链接，每一步都有可检查的中间产物。

为什么要学这个

不懂这条链路，你就只能靠"改一改、烧一烧、看现象"试错。懂这条链路，报错信息会直接告诉你问题在哪一层：是头文件路径错（预处理）、语法/类型错（编译）、目标架构不匹配（汇编）、还是段放不下、符号重复（链接）。嵌入式里最常见的启动失败，八成死在链接阶段的向量表与段布局，而不是 C 代码写错。

一、预处理：文本替换，不理解语法

gcc -E 展开 #include、#define、条件编译，产出 .i 文件。这一层出错通常是"找不到头文件""宏展开后类型不匹配"。它不看类型，所以宏写错时的报错往往指向宏展开后的位置，让人误以为是别处的语法问题——用 -E 把 .i 打出来看，一眼就能定位。

二、编译：C 到汇编，做类型检查与优化

gcc -S 把 .i 转成 .s 汇编。这里完成语法/类型检查、寄存器分配、优化（-O0/-O2/-Os）。-O0 便于单步调试，-Os 便于体积，-O2 兼顾速度。注意：优化等级越高，变量可能被放进寄存器甚至优化掉，这正是 volatile 存在的原因（D41 展开）。

三、汇编：汇编到目标文件

gcc -c 把 .s 转成 .o（ELF 可重定位目标文件），内含符号表、各段内容、重定位信息。此时地址全是相对的，未定义符号留空等链接解决。用 arm-none-eabi-objdump -d 可以直接反汇编 .o，确认某函数到底被编成了什么指令。

四、链接：拼装地址与段布局

链接器按链接脚本（.ld）把多个 .o 的段放到指定地址：.isr_vector 必须在 Flash 起始，.text 紧随其后，.data 的初值存 Flash、运行时复制到 RAM，.bss 只在 RAM 占位不占 Flash。链接出错的三类典型：region overflow（Flash/RAM 放不下）、multiple definition（重复定义）、undefined reference（找不到符号）。链接完成后产出 .elf，再 objcopy 成 .bin/.hex 用于烧写。

五、为什么必须先看 size 与 map

arm-none-eabi-size 给出 text/data/bss 三个数：text+bss 决定 Flash 与 RAM 的余量口径（data 两头都占）。map 文件给出每个函数/变量的具体地址与大小，是排查"RAM 不够""某个库吃掉 8KB"的唯一权威依据。不带 map 的工程，等于闭眼估体积。

# 1. 预处理：看宏与头文件展开结果
gcc -E $CFLAGS main.c -o build/main.i

# 2. 编译：生成汇编，检查优化后是否还有你要的语句
gcc -S $CFLAGS build/main.i -o build/main.s

# 3. 汇编：生成可重定位目标文件
gcc -c $CFLAGS build/main.s -o build/main.o

# 4. 链接：按链接脚本落到 Flash/RAM 地址
arm-none-eabi-gcc -T link.ld $CFLAGS build/main.o -o build/app.elf -Wl,-Map=build/app.map

# 5. 体检：体积与符号
arm-none-eabi-size build/app.elf          # text / data / bss
arm-none-eabi-objdump -d build/main.o | head -40   # 看实际指令
arm-none-eabi-nm --size-sort -S build/app.elf | tail -20  # 谁最占体积

# 6. 生成烧写用镜像
arm-none-eabi-objcopy -O binary build/app.elf build/app.bin

工程追问（能答上来才算懂）

-mcpu=cortex-m4 与 -mthumb 少一个会怎样？

少 -mthumb 会生成 ARM 指令集代码，Cortex-M4 只支持 Thumb/Thumb-2，运行即 HardFault 或根本链接失败；少 -mcpu 则优化与浮点指令选择出错，体积与性能都不对，浮点运算可能落到软件模拟。

为什么 .data 段的初值要存在 Flash 里？

RAM 掉电即失，初值必须固化在非易失的 Flash。启动文件在 main 之前把 Flash 中的初值复制到 RAM 的 .data 段，同时把 .bss 段清零。这也解释了为什么启动文件里那两个循环不能删。

编译通过、链接通过，烧进去却不跑，最可能在哪一层？

在链接产物的布局层，而不是 C 代码层。典型是向量表没落在 Flash 起始地址、初始 MSP 值非法、或 .ld 里 RAM 长度写得比实际小导致栈顶越界。此时看 map 中 .isr_vector 的地址与 .elf 头部入口点即可确认。

SWD 与 JTAG：调试通路的角色分工

A 类10-28 周1工具链

来源：Yiu《ARM Cortex-M3与Cortex-M4权威指南》第3版 调试特性章节

今日目标

能画出 PC—调试器—目标板 的连接与协议链

关键点

SWD 只用 SWCLK/SWDIO 两根线，走 ARM 的 ADI 协议；ST-Link 是 USB 到 SWD 的桥，OpenOCD 是 PC 侧协议实现，三者任一环断连都表现为连不上目标

动手三步
  1. 用 ST-Link 连接并在 OpenOCD 打印目标 IDCODE；
  2. 故意接反 SWDIO/GND 复现失败并记录报错；
  3. 尝试 connect under reset 模式
精讲 · 深度版（约 2374 字）

调试器连不上，九成不是调试器坏，而是目标板没给它一个可用的"握手现场"。

为什么要学这个

SWD 是你唯一能看见芯片内部的眼睛。没有它，你只能靠串口打印和 LED 猜程序死在哪。而它连不上时，新手第一反应是换线、换调试器、重装驱动——真正原因通常只有四类：目标没供电、时钟没跑、复位被拉住、调试口被程序禁用。把这四类按顺序量一遍，五分钟能解决的问题不该耗一下午。

一、SWD 只要两根信号线，但需要完整的参考地

SWDIO 双向数据、SWCLK 时钟，加上 GND 与目标电压参考（VREF/VAPP），共四根即可完成调试与烧写。相比 JTAG 的五线，SWD 引脚更省、时序更简单。关键点是 GND 必须真正共地——用长排线只接信号不接地，会出现"偶尔能连、一碰就断"。

二、握手发生在内核上电之后，不是上电即通

调试器上电后先发线序切换序列，再读 IDCODE 确认目标存在。这要求内核已经有时钟（HSI 默认可满足）、未被复位拉住、且调试模块没被关闭。所以"目标板没供电"和"芯片被程序关掉调试口"表现完全一样：都读不到 IDCODE。

三、连接模式决定能否抢在程序之前接管

Normal 模式先复位再连，程序跑起来后才停；Connect under reset 模式在复位释放前就接管总线，专门对付"程序一跑就把引脚复用掉或进低功耗"的板子；Attach 模式不复位，用于分析已运行现场。三者的差别不是玄学，是谁先拿到总线控制权。

四、读保护与选项字节是一条隐形锁

芯片若被设置读保护（RDP），调试器会读到全 0 或直接拒绝连接，此时正常连接流程彻底无效，只能整片擦除解锁（同时清空程序）。这不是故障，是安全机制——所以量产板插上调试器连不上时，先确认是不是故意锁的。

为什么把 SWCLK 降速能解决一部分连接问题？

长排线、无地线回流、上拉不足都会让信号边沿变缓并引入串扰，高速时采样点落在不稳定区间。降速等于加大时序裕量，代价只是烧写变慢。这是现场最快的验证手段，也是判断"信号完整性 vs 逻辑故障"的分水岭。

程序里把 SWD 引脚复用成普通 GPIO，会发生什么？还能救吗？

调试口一旦被复用，内核调试模块失去通路，Normal 模式彻底连不上。此时用 Connect under reset：调试器在复位释放前接管总线，抢在程序配置引脚之前停住 CPU，就能重新烧写正确固件。这也是为什么低功耗/量产固件必须保留救砖路径。

调试器能读到 IDCODE 但烧写失败，问题在哪一层？

在 Flash 控制器层，不在 SWD 层。常见是 Flash 被写保护、供电在擦除瞬间跌落、或时钟配置不满足 Flash 编程时序要求。此时看烧写报错的具体阶段（erase/program/verify），分别对应保护位、电源、时序三类原因。

能按顺序复述上电到 main 的六个步骤

关键点

动手三步
  1. 在 Reset_Handler 首行打断点单步；
  2. 观察 MSP 初值来自向量表第 0 项；
  3. 把 .bss 清零代码注释掉，看全局变量残值
精讲 · 深度版（约 3446 字）

程序没进 main，先别怀疑 C 代码——芯片在 main 之前已经跑了几百条汇编，你怀疑的那行还没轮到。

为什么要学这个

断点打不到 main、全局变量初值不对、加了构造函数就死机、换块板子同一工程跑不起来——这四类问题占调试时间的一大块，成因全在 main 之前的启动代码里。启动流程是你从没写过、却每天在跑的代码，把六步背下来，「不跑」就变成一个能逐段取证的清单。

一、复位瞬间：内核只做两件事

复位释放后，Cortex-M4 不执行任何代码，直接从 0x00000000 取第一个字装进 MSP，从 0x00000004 取第二个字装进 PC。注意是取「地址 0 与地址 4」的内容，不是调用函数。F407 在 BOOT0=0 时把 Flash 别名到 0 地址，于是这两个字来自 0x08000000 处向量表的前两项：栈顶值与 Reset_Handler 地址。这就是栈顶写在链接脚本、向量表写在启动文件、二者必须对齐同一份链接结果的原因。

二、Reset_Handler：三段固定动作

复位向量指向的 Reset_Handler 只做三件事：搬 .data（初值从 Flash 的 _sidata 拷到 RAM 的 _sdata）、清 .bss（_sbss 到 _ebss 写 0）、调 SystemInit 后 BL main。有初值的全局变量并不住在 RAM 里，是每次上电现拷的——这解释了为何掉电后它还能是 5。这两段循环若被链接脚本符号写错，表现就是初值随机，或清到了栈区导致一进 main 就 HardFault。

三、SystemInit：FPU、向量表、时钟

ST 的 SystemInit 做三件容易被忽略的事：使能 FPU（CPACR 的 CP10/CP11 置全 1）、把 VTOR 设为 VECT_TAB_OFFSET（默认 0x08000000，做 bootloader 时必须改）、按宏配 PLL 与总线分频。很多人以为浮点没开只是慢，实际是直接异常：Cortex-M4 默认禁用协处理器，一条 VMUL 就进 UsageFault，现象却像跑飞。

四、__libc_init_array：C 运行时最后一步

SystemInit 之后、main 之前，newlib 会遍历 .preinit_array 与 .init_array 并逐个调用。C++ 全局对象构造、__attribute__((constructor)) 都挂在这里。它依赖链接脚本生成 __init_array_start/__init_array_end 符号；符号缺失时构造函数静默不执行，现象是「对象成员全是 0」，比崩溃更难查。

五、向量表与弱定义：中断没反应的真相

向量表前 16 项是内核异常，第 16 项起是外设中断，每一项都是一个地址。启动文件把全部向量 weak 定义成同一个 Default_Handler 死循环——「开了中断却没写服务函数」时程序停在那里，不是没进中断，是进了弱定义。要让中断生效，函数名必须与向量名逐字一致，拼错一个字母就静默回落，且编译器不报警。

extern int main(void);

void Reset_Handler(void)
{
    uint32_t *s = &_sidata, *d;
    for (d = &_sdata; d < &_edata; ) *d++ = *s++;   /* 1 搬 .data */
    for (d = &_sbss;  d < &_ebss;  ) *d++ = 0;      /* 2 清 .bss  */

main 为什么不允许返回？返回了会怎样？

Reset_Handler 用 BL 调 main，返回地址紧随其后。若那里是死循环，程序静默停住像卡死；若没写死循环，返回地址可能是随机数据，PC 跳非法地址触发 HardFault。裸机没有「退出」这个概念，所以标准写法是末尾 for(;;)。

为什么不能上电先 memset 整片 RAM 再搬 .data？

MSP 此时已指向栈顶，启动代码自身的局部变量与返回地址就在栈里，盲清会把它清掉。工程做法是由链接脚本给出 .bss 起止符号，只清 .bss 段，不碰栈与已搬入的 .data。

记住这三条

  • 复位瞬间硬件只做两件事：从 0x0 取 MSP，从 0x4 取 PC。
  • Reset_Handler 三段：搬 .data、清 .bss、SystemInit 后进 main。
  • main 之前还有 __libc_init_array，C++ 构造挂在这里。

  • 中断函数名拼错，weak 静默接管，现象是「中断没反应」且零告警。
  • 改 VECT_TAB_OFFSET 忘同步改 Flash 起始，能烧进去但一中断就飞。

为什么要学这个

手写绝对地址能跑，但换芯片就全废。CMSIS 把「手册里的偏移」翻译成可直接引用的结构体，理解它怎么翻译，才知道为什么改错头文件会写坏别的外设。

一、三层结构，各管一段

CMSIS-Core（core_cm4.h）只定义内核：NVIC、SysTick、SCB；设备头（stm32f4xx.h）定义 GPIO_TypeDef 等外设结构体与基址；启动文件与 system_stm32f4xx.c 提供向量表与 SystemInit。

二、结构体就是手册的偏移表

GPIO_TypeDef 的成员顺序严格等于 RM0090 的偏移顺序（MODER 0x00、OTYPER 0x04、OSPEEDR 0x08、PUPDR 0x0C、IDR 0x10、ODR 0x14、BSRR 0x18、LCKR 0x1C、AFR 0x20 两字），编译器按成员大小累加偏移，所以 GPIOA->BSRR 才正好落在 0x40020018。成员类型全是 volatile uint32_t。

三、SystemInit 与时钟的关系

精讲 · 深度版（约 3491 字）

串口乱码、USB 不认、定时器差 4 倍——三个看似无关的故障，根子是同一张时钟树配错了一格。

为什么要学这个

时钟是唯一一个「配错后所有外设一起坏，但代码看起来完全正确」的模块。它决定了 Flash 等待周期、总线上限、串口波特率、定时器计数频率、ADC 采样时钟，乃至 USB 能不能枚举。把 8MHz 到 168MHz 的每一格自己算一遍，串口乱码这类故障就变成算术题：先看 PCLK，别急着换线。

一、两级倍频：PLL 公式必须会算

VCO = (HSE ÷ PLLM) × PLLN，SYSCLK = VCO ÷ PLLP，另有 48MHz = VCO ÷ PLLQ 专供 USB/SDIO/RNG。8MHz 配 168MHz 的一组解：PLLM=8 得 1MHz 参考（RM0090 建议 PLL 输入 1–2MHz、VCO 100–432MHz），PLLN=336 得 336MHz，PLLP=2 得 168MHz，PLLQ=7 得 48MHz。四个参数是一组解，改一个必须重算其余。

二、总线分频与「定时器 ×2」规则

HCLK 上限 168MHz，APB1 上限 42MHz，APB2 上限 84MHz。关键细节：APB 预分频不为 1 时，该总线上的定时器时钟自动 ×2。故 168MHz 系统里 APB1 配 /4 得 42MHz，TIM2–7 实跑 84MHz；APB2 配 /2 得 84MHz，TIM1/8–11 跑 168MHz。算定时器重装值时漏这一步，定时正好差 2 倍。

三、Flash 等待周期：先加等待再提速

Flash 读速度跟不上 168MHz 内核。DS8626 表 10：2.7–3.6V、150–168MHz 需 5 个等待周期，120–150MHz 需 4 个，逐档递减。ACR 写 LATENCY=5 并开 PRFTEN/ICEN/DCEN 才拿得回性能。顺序必须「先写 ACR，再切 SYSCLK」，反过来会在切换瞬间取到错指令，现象是随机跑飞。

四、切换是一套握手，不是一次赋值

顺序：置 HSEON 等 HSERDY→改 PLLCFGR（PLL 必须处于关闭态才可写）→置 PLLON 等 PLLRDY→写 ACR→CFGR 的 SW 选 PLL→轮询 SWS 直到为 PLL。SWS 是硬件回执，只有它变了才算真切过去；跳过它继续初始化，外设会落在旧时钟上，现象是「偶尔能跑、偶尔全错」。

五、时钟如何长成波特率

过采样 16 时 USARTDIV = fPCLK ÷ (16 × baud)，过采样 8 时除以 8 × baud。115200 在 42MHz 上算得 22.79，实测波特率有零点几的误差，一般可接受；但把 PCLK1 误当 84MHz 来算，误差直接翻倍，接收端全帧错。

精讲 · 深度版（约 3259 字）

灯不亮不是代码没跑，是引脚还停在复位默认的输入态——GPIO 复位后没有一个是输出；而推挽配成开漏，灯只会微亮。

为什么要学这个

GPIO 是唯一一类「每个功能外设都要经过它」的器件：串口、SPI、PWM、ADC、外部中断，最终都落在某个引脚的几种模式上。灯不亮、按键乱跳、波形边沿难看、仿真器突然连不上，四类现象里有一半根子在 MODER/PUPDR/AFR 这三组位。把八种模式的内部通路想清楚，接线前就能判断该不该加上拉。

一、四个开关决定一个引脚

每个引脚内部有四个可配环节：MODER 决定信号往哪走（输入/输出/复用/模拟），PUPDR 决定挂不挂内部上下拉，OTYPER 决定输出级是推挽还是开漏，OSPEEDR 决定输出驱动的压摆率。复用模式下还要 AFR 选具体外设通道。四者组合出官方文档里的八种模式，任何「引脚行为不对」都能拆到这四组位。

二、输入侧：浮空、上下拉、模拟的区别

浮空输入把引脚直接接到施密特触发器，电平由外部决定；不接东西时读数随机，手一碰就变——按键悬空乱跳就是这个原因。内部上/下拉约 30–50kΩ（典型 40kΩ），只能做「默认电平」，驱不动负载。模拟模式下施密特触发器被断开，引脚直连 ADC 采样网络；此时若还开数字上下拉，会直接污染采样值。

三、输出侧：推挽与开漏的适用边界

推挽输出由 PMOS/NMOS 互补驱动，能同时拉高拉低，适合直接驱动 LED、MOS 栅极。开漏只有 NMOS，高电平靠外部上拉，因此能做电平转换（3.3V 器件驱动 5V 上拉总线）与线与（I2C 的 SDA/SCL 必须开漏）。开漏不加上拉时测到的是高阻，灯微亮或不亮，很多人误判为「引脚坏了」。

四、速度位不是「越高速越好」

OSPEEDR 调的是输出级压摆率：档位越高边沿越陡、上升时间越短，同时 EMI 与过冲越大。驱动 LED、继电器这类慢速负载用低档即可；SPI、SDIO 这类高速信号才需要高档。全部配成最高速是新手常见做法，代价是辐射变差、长线振铃，示波器上会看到明显的过冲与振铃。

五、两个易踩的坑：AFR 与 SWD 引脚

复用功能由 MODER=10 加 AFR[0]/AFR[1] 的 4 位通道号共同决定，只配 MODER 不配 AFR 引脚不会有波形；且一个引脚同时只能选一个 AF，选错就是「无输出」。另外 PA13/PA14 复位后是 SWDIO/SWCLK，把它们配成普通 GPIO 或模拟，仿真器立刻掉连接，只能靠 BOOT0 或 connect under reset 抢救。

整端口输出（如并口屏 8 位数据）为什么不能逐位改 ODR？

逐位改 ODR 是「读—改—写」三步，8 位要重复 8 次，每次都可能被打断，且中间态会短暂输出错误电平。做法是先在影子变量里拼好整字节，再一次写入 ODR，保证 8 位同时更新。

开漏输出为什么必须配上拉？不接会怎样？

开漏只有下拉管，写 1 时引脚处于高阻而非高电平，电压由外部决定。不接上拉时量到的是悬浮电平（随负载与环境漂移），做 I2C 会直接通信失败，做电平转换则永远到不了高电平。

  • MODER/PUPDR/OTYPER/OSPEEDR 四组位决定八种模式。
  • 复用功能必须同时配 MODER=10 与 AFR 通道号。
  • 输出速度档位按信号边沿需求选，不是越高越好。

易错

  • 忘开 RCC_AHB1ENR 就写 MODER，寄存器读写正常但引脚毫无反应。
  • 把 PA13/PA14 配成普通 GPIO，调试器从此连不上，需 connect under reset 抢救。
  • 模拟输入仍开内部上下拉，ADC 采样被偏置，误差可达数十个码。

寄存器读改写：为什么置位要用 BSRR 而不是 ODR

A 类11-05 周2寄存器

来源：RM0090 通用 I/O 章节 · BSRR 寄存器

今日目标

能说明读改写在多任务或中断场景下的竞态风险

关键点

ODR 是读-改-写三步，中断插进来会丢更新；BSRR 是只写寄存器，写 1 生效写 0 无影响，天然原子，且高 16 位可复位

动手三步
  1. 用 ODR 异或翻转并在中断里同时改同一端口观察丢步；
  2. 换 BSRR 复测；
  3. 只用一条 BSRR 写入同时置位与复位两个引脚
精讲 · 深度版（约 3121 字）

偶发丢灯、偶发配置没生效，八成不是逻辑错，是一条 |= 被中断劈成了两半。

为什么要学这个

「我明明写了置位，为什么灯偶尔不亮」是裸机阶段最难查的一类 bug：单步永远正确、加打印就消失、示波器上一个月出现两次。根因是 C 的 |= 在汇编里是三步，中间可以被任何中断切开，两个上下文各写一次，后写把前写覆盖掉。BSRR 之所以是新手的第一个「硬件级并发原语」，就在于它把读改写压成了单次写入。

一、|= 的真实形态：LDR、ORR、STR

GPIOA->ODR |= (1u << 5) 在 -O0 下编译为 LDR r0,[ODR] → ORR r0,r0,#0x20 → STR r0,[ODR]，三步之间可插入任意中断。时序：主循环先读到 ODR=0x00，中断把 bit5 置 1（ODR=0x20），中断返回后主循环把自己算的 0x01 写回，bit5 消失。这就是「丢灯」，且丢的是别人写的位，不是自己写的位。

二、BSRR：写 1 生效，写 0 无影响

BSRR 低 16 位 bs 写 1 置位、高 16 位 br 写 1 复位，写 0 的位完全不受影响，且一条 STR 完成全部动作，中间没有可插入的窗口。同一位若 bs 与 br 同时写 1，硬件规定置位优先（RM0090 8.4.7）。BRR（偏移 0x28）只做复位，等价于只写 BSRR 的高 16 位，二者选一即可。

三、什么时候反而必须直写 ODR

整端口并行输出——并口 LCD 的 8 位数据、数码管段码——要求 8 位同时更新，逐位 BSRR 会产生中间态（先高后低的瞬态错误码）。做法：在影子变量 uint16_t shadow 里拼好完整字节，再一次 GPIOA->ODR = shadow。此时写的是完整值而非读改写，本身不存在竞态，前提是影子变量只由一个上下文维护。

四、volatile 管的是「不被优化掉」

寄存器指针必须是 volatile，否则 while (!(GPIOA->IDR & 0x01)) 这种轮询会被编译器提到循环外变成死循环——它认为没人会改那块内存。但 volatile 只保证每次都真实访存，不提供任何原子性：把 |= 改成 volatile 读写三步，竞态照旧。这是两个正交问题，混为一谈就会写出「加了 volatile 怎么还丢」。

五、硬件没有单写寄存器的场合

PLLCFGR、TIMx_PSC 这类寄存器只能整体读改写。此时要么先算好完整值一次写入（无并发写者时最干净），要么用 __disable_irq()/__enable_irq() 或 BASEPRI 临界区把三步包起来。F4 还提供位带别名区（别名地址 = 0x42000000 + 字节偏移×32 + 位号×4）可对单个位做原子读写，但一次访问要算地址，性能不如 BSRR，只在需要「原子读某一位并据此判断」时才用。

BSRR 为什么不需要关中断就安全？

它没有读这一步：一次存储写指令，硬件按位解释「写 1 动作、写 0 忽略」。没有中间态，也就不存在被插入的窗口，中断在写指令之前或之后发生都不影响结果。

位带和 BSRR 都能原子操作，选哪个？

只做置位/复位选 BSRR：一条指令、无需算地址、还能一次改多个位。需要对单个位做「原子读—判断—回写」的复合操作（如测试并置位的信号量）才用位带，因为它把一位映射成一个可读写的字，读与写各自原子。

记住这三条

  • |= 在汇编里是三步，中间可被中断打断，这是丢位的根因。
  • BSRR 写 1 生效、写 0 忽略，一条指令完成置位或复位，同一位置位优先。
  • volatile 保证真实访存，不提供原子性，两者不能互相替代。

易错

  • 以为 volatile 能解决竞态，加了 volatile 继续丢位。
  • 整端口逐位更新，中间态被外设当作有效数据采走。
  • 临界区里调用可能阻塞的函数，把系统节拍一起关掉。

自测：主循环与中断都要置 PA5 和 PA6，为什么用两次 BSRR 而不是 ODR |= 0x60？

看答案

两次 BSRR 各自原子，互不覆盖；ODR |= 0x60 是读改写，两侧并发时会丢掉对方刚写的位。

原子性来自「单次写入 + 写 0 无影响」，与是否一次改多个位无关。

精讲 · 精简版（约 1392 字）

为什么要学这个

「编译通过了」不等于「装得下、跑得稳」。size 给出三个数值的边界，map 给出每个字节的归属；读不懂它们，就只能靠「加个变量试试」来猜 RAM 够不够。

一、text/data/bss 三个数各管一件事

text 是代码加只读常量，占 Flash；data 是带初值的可写变量，初值存 Flash、运行时装进 RAM，故两头都占；bss 是零初始化变量，只占 RAM，启动时由启动代码清零。三者之和不是 Flash 总量，必须按「Flash = text + data、RAM = data + bss」分别核对。

二、map 的作用是按符号归账

map 里先给段汇总（.isr_vector、.text、.data、.bss、.heap、.stack），再按符号列出地址与大小，按大小排序就能一眼看出谁在吃空间——常见大户是浮点格式化、printf、查表和大的全局缓冲。

三、栈与堆是看不见的那部分

启动文件里 ._user_heap_stack 只预留大小，运行期实际用量全靠估算。局部大数组、深递归、中断嵌套都会让栈超限，表现是随机 HardFault 或变量被莫名改写——这类故障在 size 里完全看不出。

精讲 · 精简版（约 1241 字）

用 printf 查时序问题，等于用秒表量纳秒。

为什么要学这个

四种手段的时间分辨率与侵入性差几个数量级。选错工具不是效率低，而是会得到错误结论：printf 本身耗时毫秒级，用它测中断间隔必然失真。

一、按时间尺度分层

printf 适合状态与流程（ms 以上）；断点适合逻辑分支（停在那一刻看变量）；逻辑分析仪适合协议与多路时序（ns–µs，且不打断 CPU）；示波器适合模拟量、上升沿与电源纹波（看波形质量）。

二、侵入性要一起考虑

断点会暂停 CPU，改变时序甚至让竞态消失；printf 占用串口与 CPU，且在中断里可能破坏实时性；分析仪与示波器是外部观测，几乎零侵入，代价是要有引脚可探。

三、CPU 周期计数补足中间层

DWT->CYCCNT 以 CPU 周期计时，误差在一个周期内，适合量函数耗时与中断响应，比 printf 精确得多，也不需要外部设备。前提是使能 DWT 并注意计数器 32 位回绕。

为什么要学这个

前十三天学的是零件，今天要的是装配能力：给定「PA1 上的 LED 要闪」，能独立推出需要改哪几个寄存器、按什么顺序、用什么证据确认每一步生效。这条链走通，后面的外设都是同一套骨架换个名字。

一、因果链只有四环

时钟使能 → 引脚模式 → 输出电平 → 时间基准。四环任一缺失都表现为灯不亮或常亮，而现象几乎相同，所以必须按顺序验证，而不是并发猜测。

二、顺序不可交换的原因

寄存器写操作需时钟才生效；MODER 未置位时写 ODR 无效；时间基准缺失则灯亮着不动。顺序：时钟、模式、电平、节拍。

三、用读数代替猜测

每环都留一个可验证读数：RCC->AHB1ENR 的 EN 位、MODER 对应两位、ODR 对应位、以及一次翻转周期。四读数齐了，故障必然在硬件侧（LED 极性、限流电阻、焊接）。

要求 PA1 上的 LED 以 2Hz 闪烁，你会依次写哪几处？
